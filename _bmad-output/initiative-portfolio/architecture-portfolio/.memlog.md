- (decision) AD-1 (ADOPTED): one application, one small database - public pages and admin routes in a single codebase and single deployable; the DB is the shared source of truth for projects, section text and the contact email. Binds all epics. Prevents: two deployables, a rebuild pipeline that can silently serve stale or empty content, split security surfaces, doubled hosting cost against RULE-7.
- (decision) AD-2: write rule - the public surface never writes persistent site data. Contact messages are stored in the DB AND forwarded to email (store + forward, chosen over forward-only for the audit trail); bookings never touch the DB, they live entirely in the scheduler. The admin area is the only other writer. Binds contact-form epic, booking epic, admin epic, foundation epic. Prevents: epics adding public write paths into the site DB, booking data duplicating into local tables, scope creep toward a message inbox unless explicitly chosen.
- (decision) AD-3: admin gains a minimal read-only messages inbox - a simple list of stored contact messages (who, when, what) inside the admin area, as a deliberate scope addition beyond FR-11/FR-12; the DB copy is otherwise RULE-5's safety net. Binds admin epic, contact-form epic. Prevents: an unstated gap where stored messages are unreadable without raw DB access; also prevents a full mail-client feature set (no reply, no delete workflows, no search beyond maybe-none). Flag for finalize: capability not in the PRD - offer Sofia a ticket update so PRD and spine do not diverge.
- (question) Message retention is open (part of OQ-5): stored messages are personal data; a purge default (e.g. 90 days) vs keep-forever must be answered by Hamza before launch. Owner: Hamza. Needed before launch; blocks nothing in the build.
- (decision) AD-4 (ADOPTED by confirm): paradigm is a modular monolith - three modules (public: read-only visitor surface; admin: the only DB writer, plus messages inbox; integrations: ports+adapters for scheduler, email service, captcha). Dependency rule: public and admin may use integrations; integrations never reach back into public or admin. Binds all epics. Prevents: cross-module reach-in, hand-rolled vendor calls outside the integration ports, public code growing write paths.
- (direction) Stack direction changed by owner before binding: the Spring Boot stack was laid out but never bound; owner chose Django + React SPA instead, for the admin page and modern frontend learning. Tradeoffs stated and accepted: two frameworks, DRF API layer, cross-origin auth, slower build, heavier hosting vs RULE-7. Spring Boot AD never existed - no superseded ID needed.
- (decision) AD-5 (amends AD-1 partially): stack is Next.js + Django - React for everything, chosen against the coach's React-admin-only lean with tradeoffs accepted. Next.js 16.x (SSR/SEO) on Vercel serves the public site AND the admin SPA; Django 6.1.x + DRF is the JSON API and the only DB accessor; PostgreSQL as data store. One codebase and one DB still hold; 'one deployable' from AD-1 no longer holds - two deployables (Vercel + Python host). AD-2 write rule survives unchanged and strengthens: the UI layer never touches the DB; all access goes through the Django API. Binds all epics. Prevents: the frontend fetching the DB directly, a third app appearing, admin logic living in the UI.
- (constraint) Hosting constraint for epic 7 (from AD-5 + RULE-4): the Django API must be warm - free tiers that spin down (30-60s cold start) break RULE-4 on every cold visit because public pages fetch content from the API. Either an always-on host within RULE-7's ceiling, or an explicit owner decision to accept cold starts. Vercel Hobby (free) assumed for Next.js; owner proposed free Django hosting - cold-start risk flagged 2026-11-22.
- (decision) AD-6: admin auth is a Django session cookie - httpOnly, Secure, SameSite=None with CSRF protection (Django-native), chosen over JWT for XSS-resistance and less code; the admin SPA sends credentials cross-origin to the API. Binds admin epic, foundation epic (auth setup). Prevents: tokens in JS-readable storage, hand-rolled CSRF, per-epic auth inventions.
- (decision) Environments: dev + prod only, no staging (owner); deploy = merge to main. Fits a solo-build single-admin site. Binds all epics. Prevents: epics assuming a staging environment or preview-deploy workflow exists.
- (assumption) API error shape: one JSON envelope for every API error ({error: {code, message}}) so the React app handles failures uniformly. ASSUMPTION - not explicitly confirmed by owner; safe default, revisit only if a need appears.
- (decision) Analytics: Vercel Web Analytics keeps R13 in v1 - cookieless, lightweight (RULE-4 safe), free tier, conversion events (booking click, form submit) as custom events, read in the Vercel dashboard. Binds foundation epic (install), launch epic (verify metrics readable). Prevents: dropping R13 silently, heavy analytics scripts in the first screen, a consent-banner requirement appearing from the analytics choice.
- (decision) AD-7: RULE-5 second channel is the admin messages inbox - every email send (contact message, booking notification) records a delivery status (sent/failed); failed sends appear marked in the inbox, making silent loss impossible for Hamza. Booking notifications ride the scheduler's own delivery, checkable in the scheduler dashboard. Binds contact-form epic, booking epic, admin epic. Prevents: silently swallowed send failures, a second alerting service being added unprompted.
- (decision) AD-8: project screenshots live in object storage, never on the server's local disk (ephemeral-disk trap on free Python hosts); Django stores only URLs. Vendor deferred to the admin epic - Cloudinary or Supabase Storage suggested (free tiers), same integration-port pattern as email/captcha. Binds admin epic, project-proof epic, foundation epic. Prevents: screenshots vanishing on redeploy, base64-in-DB payloads, per-epic file handling.
- (decision) AD-9: single-adapter rule for shared external services - one email service, one captcha vendor, one scheduler: each behind exactly one integration port; the booking epic must reuse the contact epic's email adapter (per ticket decision) and the shared captcha, never add its own. Vendor choices stay with the owning epics (email+captcha: contact epic, Q3; scheduler: booking epic, inherited; media storage: admin epic). Binds contact-form, booking, admin epics. Prevents: duplicate adapters per epic, two captchas on two forms, parallel email vendors.
- (decision) AD-10: content freshness contract between the two deployables - public pages are server-rendered by Next.js from the Django API; a Django admin save triggers on-demand revalidation of the affected Next.js pages (webhook), with a short time-based revalidate window (e.g. 60s) as fallback. Binds foundation epic (plumbing), admin epic (trigger), project-proof/home epics (consumers). Prevents: stale proof after an admin edit (the site's core promise is current content), each epic inventing its own cache strategy.
- (event) Reviewer gate pass 1 complete: lint clean; four reviews (reconciliation, rubric, tech-currency, adversarial) applied in one rewrite. AD-2 amended (per-module table ownership; public surface has exactly one write endpoint), AD-5 (Next.js 16.4.x security pin, PostgreSQL 18, Vercel as owner-proposed assumption ratified by epic 7), AD-6 (one public origin via Next.js /api proxy - no CORS; foundation owns /api/auth, CORS/CSRF env, disables built-in admin), AD-7 (delivery_status enum pending/sent/failed owned by messaging; booking notifications via shared email port; inbox + best-effort independent secondary alert), AD-8 (storage port provisioned at foundation; vendor by admin epic but resolved before epic 3 seed; multipart through Django only; 10MB cap), AD-9 (captcha verifies Django-side; signed booking handoff to scheduler API; site key via foundation config endpoint), AD-10 (foundation builds both webhook halves + path map), new AD-11 (shared SSR fetch layer, 3s timeout, stale-serve degradation; warmth owned by launch epic), new AD-12 (operational envelope: dev+prod, daily backups with tested restore, uptime monitor, 99% monthly conversion-path availability).
